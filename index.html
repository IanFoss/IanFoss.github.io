The artifacts in my ePortfolio fit together as a progression of improvements to one Android inventory management application originally created in CS 360. Enhancement One: Software Design and Engineering

This enhancement modernized the Android app from Java to Kotlin and improved account validation.

View Enhancement One Code

Artifact Description

The artifact used for this enhancement is a mobile application that was created in a course I previously took at SNHU, CS 360 Mobile Architecture and Programming. It is an inventory management application developed in Java that supports persistent data for users and items using the Room database. The app allows users to create an account and log in. They then navigate to the inventory screen, where they can view existing inventory items, as well as add, edit, and delete items.

Enhancement Justification

I selected this item for the artifact because the application was very basic in its original form, which provided many opportunities for improvement. The item also represents a complete application because it has multiple connected parts that provide value and could be used in a real-life setting, rather than functioning only as a coding exercise. Converting the project to Kotlin provided a way to modernize the application because Kotlin is the standard programming language for Android applications.

This artifact showcased my skills in several areas. It allowed me to demonstrate Android architecture skills, including using activities for screen behavior, Room entities for database tables, DAO interfaces for database queries, repositories for data access, and an adapter for displaying inventory items in a RecyclerView. I was also able to demonstrate my ability to take an existing application and identify areas for improvement after analyzing the existing Java code.

The artifact was improved by converting the Java classes to Kotlin classes, which reduced boilerplate and improved readability. Kotlin features such as null safety, data classes, and lambda expressions were used to make the code less prone to errors. Input validation was also improved. I added validation to prevent duplicate and blank usernames, blank item names, and negative item quantities. I also added stronger password requirements to improve the baseline security for accounts.

Course Outcomes

I feel I met the course outcomes I had planned to meet for this enhancement. The enhancement strongly aligns with course outcome four because it uses modern Android tools and computing practices that provide real-life value in inventory tracking. The enhancement also improved the prospect of collaboration because it led to code that is more readable and easier to maintain. If other developers were hypothetically working on the application, these improvements would support a more effective collaborative team environment.

Reflection

This enhancement provided a strong opportunity to learn about the Kotlin programming language and Android development patterns. I gained a better understanding of how Kotlin null safety works. I had to think more carefully about which values could potentially be null and where it was appropriate to use the question mark operator to allow null values. For example, the Room query that searched for a user needed to potentially return a null UserEntity object if no user was found.

Before the enhancement, the code used Java Consumer patterns to return data. Changing those to Kotlin function types cleaned up the code and made it easier to read. One challenge I had was avoiding breaking the app while changing the code to Kotlin. Several times, I made changes that caused the app to crash in certain areas, which required additional debugging and refinement.

Enhancement Two: Algorithms and Data Structures

This enhancement added search, sort, and filter functionality to the inventory list.

View Enhancement Two Code

Artifact Description

The artifact I chose for this enhancement was again the Android application I created in my previous SNHU class, CS 360 Mobile Architecture and Programming. It is an inventory management app that supports persistent data for users and inventory items using the Room database. I chose this artifact because it already used data structures and algorithms at a basic level and provided a strong opportunity for improvement. The list of items was an appropriate place to implement data structures and algorithms because those aspects directly affect how users can manipulate inventory data in the application.

Enhancement Justification

The artifact showcases my ability to work with list-based data. It demonstrates algorithmic thinking through the searching, sorting, and filtering features implemented in the enhancement. Search logic was added to improve usability by allowing users to find an item in the inventory without manually scrolling through the list. Filtering logic for low-stock and out-of-stock items was also added. Sorting logic was added to allow users to view items alphabetically or by quantity.

Since the application uses the Room database, the SQL queries influence the algorithmic complexity involved in fulfilling the functionality. The search and filter functionality, along with updating the RecyclerView with the altered list of items, needs to process the relevant inventory records and display the result set. From an algorithmic complexity standpoint, the worst-case time complexity for these operations can generally be described as O(n), where n is the number of items in the inventory.

For the sorting functionality, there is increased operational complexity. The Room database sorting operations are abstracted away by SQLite after the ORDER BY query is passed to it. Generally speaking, a common complexity estimate for comparison-based sorting is O(n log n). While these enhancements perform more operations than the original app, the efficiency and usability for the user are greatly improved because they no longer need to manually scroll through the list to find an item.

Course Outcomes

I believe I met the course outcomes for this enhancement that were planned in Module One. This enhancement strongly supports the course outcome of designing and evaluating computing systems using algorithmic principles. The application uses a collection of inventory objects and applies searching, sorting, and filtering logic. This demonstrates how data structures can store records and how algorithms can manipulate those records in useful ways.

This enhancement also supports the course outcome of using well-founded computing techniques. The logic for this additional functionality was implemented through Room DAO queries and repository methods. This contributed to a separation of concerns between the activity/UI logic and the database operations. I do not have any updates to my coverage plans at this time.

Reflection

This enhancement provided valuable learning experiences. I learned how to use RecyclerView in more depth. The inventory list needed to initially load every item and then display only the items that matched the search, sort, or filter criteria. This required ensuring that I was observing the most recent LiveData source and updating the adapter with the new list of items.

One challenge was ensuring that I updated all required classes while maintaining separation of concerns. It would have been easier to add all the logic directly into the inventory activity. Instead, to enhance the artifact using Android best practices, I needed to create new DAO queries, repository methods, UI logic, and repository method calls. Overall, this enhancement was a good learning experience in applying searching, sorting, and filtering logic to a real data set.

Enhancement Three: Databases

This enhancement improved the Room database schema, password security, validation, and migration handling.

View Enhancement Three Code

Artifact Description

This artifact is the same as the previous two artifacts, which is the mobile inventory management application developed for the Android OS. It was created in a previous course at SNHU, CS 360 Mobile Architecture and Programming. The application allows users to create an account, which they must do before logging in. After the user successfully creates an account and logs in, the app navigates to the inventory screen, where they can view the items in the inventory, add an item, modify item attributes, and delete items. The application uses Room to store data for user accounts and inventory items.

Enhancement Justification

I selected this artifact for my ePortfolio because the previous implementation of the database lacked several aspects that would make the implementation acceptable in a professional application, making it a strong candidate for enhancement. The artifact was improved in several ways. First, database operation validation was improved. Validation was added in the repository and application layers to ensure that duplicate items are not added to the database.

Second, the database schema for the user entity was changed to eliminate the storage of plaintext passwords. The password column was replaced with a password hash and salt. This updated the database to follow security best practices by salting and hashing user passwords rather than storing secrets in plaintext.

Finally, a Room migration was added for the inventory items. The Room database previously used fallbackToDestructiveMigration(), which erases all stored data when the schema changes. A migration was used to update the inventory item entity to include category and low-stock-threshold attributes. This showcased my skills in applying a security mindset, incorporating security by design, and prioritizing data quality and integrity.

Course Outcomes

I met the course outcomes I planned to meet in the Module One materials, which were course outcomes four and five. Course outcome four was met by using well-founded techniques and tools to provide the database migration, as well as standard security techniques that improved the security of the application’s sensitive data.

Course outcome five was met because the enhancement demonstrated a security-focused mindset by implementing input validation across multiple layers of the application and eliminating the security flaw of storing plaintext passwords in the database. I do not have any updates to the outcome coverage plan at this time.

Reflection

The process of enhancing this artifact provided a learning experience in several ways. I learned the importance of using input validation across multiple layers of the application. I already had the unique constraint applied to the name attribute of the inventory item, but initially I did not have validation to catch errors if an attempt was made to create a duplicate item. The unique constraint prevented the item from being inserted, but the program would crash. Properly handling the error at the application level prevented crashes and improved the user experience.

I also learned how to use security-related classes to generate a salt and hash user passwords. Finally, I learned that setting up a Room migration is not a catch-all for all future schema changes. Rather, it is a targeted path for changing the schema between specific database versions, where the specific changes are defined in the migration plan.
